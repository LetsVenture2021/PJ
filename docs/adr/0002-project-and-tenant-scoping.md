# ADR 0002: Project and tenant scoping

- **Status:** Accepted
- **Date:** 2026-07-29

## Context

Projects group conversations, memory, jobs, workflows, and artifacts. Future
synchronization must not turn an implicit owner-only runtime into accidental
cross-tenant access.

## Decision

Every durable domain object carries immutable `tenant_id` and `project_id`
fields. The initial local tenant is explicit rather than represented by null.
Identifiers are opaque, bounded strings generated by the server. Parent-child
scope must match and database uniqueness/indexes include tenant scope.

Scope is derived from authenticated server context, never trusted from tool
arguments or provider output. Repositories require a scope object and include
scope predicates in reads, writes, joins, searches, leases, and deletes. A
missing scope fails closed. Cross-project operations require a named action,
policy decision, explicit source and destination scopes, and audit metadata.
Provider caches and filesystem paths are namespaced and traversal-safe.

## Consequences

The domain contract is slightly more verbose, but authorization becomes
testable as a matrix. Migration assigns legacy data to the configured local
tenant and default project and records that provenance.
